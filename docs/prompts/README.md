# How to feed this to a no-code tool

`../rebuild-prompt.md` is the whole specification in one file — about 14,000
words. It is meant to be *read*, and it is too big for most tools' prompt boxes.
This folder is the same document sliced into nine pastable pieces, generated by
`scripts/split-rebuild-prompt.mjs`. **Edit the master, then re-run the script** —
never edit these by hand, or the two drift.

The brief assumes nothing about the stack: no framework, no particular database,
no component library. §4 describes the **records** the app needs rather than the
tables of any specific database, so a tool with its own built-in data layer can
follow it directly.

| File | Words | What it covers |
|---|---|---|
| `00-standing-brief.md` | ~2,600 | What the app is, the design system, the routes, the build order, the acceptance tests |
| `01-data-and-offline.md` | ~3,200 | The eighteen records, access rules, and what syncing must not break |
| `02-shopping-list.md` | ~1,000 | The shopping list and aisle settings |
| `03-recipes-and-plan.md` | ~1,900 | Library, recipe editor, the week, deriving the list |
| `04-ingredients.md` | ~1,800 | Quantities, shopping names, aggregation, aisle guessing |
| `05-people-and-roster.md` | ~500 | People, life stages, who is eating |
| `06-generator.md` | ~1,000 | The weekly generator |
| `07-import.md` | ~600 | URL and photo import, nutrition, calendar, keepalive |
| `08-today-and-cook.md` | ~2,500 | Today, cook mode, chores, pantry |

## The shape of it, whatever the tool

1. Get `00-standing-brief.md` in front of the tool **once**, and keep it there —
   in whatever it calls project knowledge, custom instructions or a system
   prompt. It is the context every other step assumes. If the tool has no such
   place, paste it as the first message of the conversation and stay in that one
   conversation.
2. Then send steps 1 to 8 **as separate messages, in order**, letting the tool
   finish and settle between each.
3. Attach the screenshots each step names. They settle in one look what a
   paragraph of layout prose only approximates.

Do not paste all nine at once even if they fit. The build order exists because
step 5 is much easier to get right when step 1 already works, and a tool given
everything at once will start at the generator.

## Tools with a built-in database and no framework choice

This is the common case — Scram and most of its neighbours. Nothing in the brief
needs changing for them, but two steps need handling deliberately:

**Step 1 is about the data, not the plumbing.** The tool already has a database,
so the useful half of `01-data-and-offline.md` is §4: the eighteen records and
their fields. Have it build those first and confirm the shape before any screen
exists. The conventions under §4 are the ones to check it actually honoured —
particularly that **deleting sets a field rather than removing the record**, and
that the six deterministic ids are not enforced with a uniqueness rule instead.

**Offline is the one thing the platform may simply not do.** §5 says so and tells
the tool to admit it rather than fake it. Read its answer honestly:

- If it supports offline use, hold it to the §5 rules and the airplane-mode test.
- If it does not, the app is still worth building — but the shopping list is now
  a page that needs signal, which is the one compromise that changes how it feels
  in a supermarket. Note it and move on; do not let the tool paper over it with
  a spinner.

Everything else — the derivation, the aggregation, the generator, the whole
design system — is unaffected by either answer.

## Tools that let you pick a stack

**Lovable** — paste `00-standing-brief.md` into **Project Settings → Knowledge**.
It is prepended to every message, so you never resend it. Then send the steps as
ordinary chat messages.

**Bolt.new** — no persistent knowledge field. Better than re-pasting: start the
project from a GitHub repo that already contains `docs/`, then say *"Read
docs/rebuild-prompt.md and docs/prompts/01-data-and-offline.md, then build step
1."* Bolt reads files in the project, so the big document costs nothing in the
prompt box.

**v0** — project-level instructions for the standing brief. v0 is strongest on
single screens, so go finer than these eight steps: feed it one `### 6.x` section
from the master document at a time.

**Replit Agent / Cursor / Windsurf** — commit `docs/` into the project and
reference files by path. These read the repo, so the master document is the
better input and this folder is redundant.

## What to watch for

The parts a tool will most likely get wrong, in rough order of likelihood:

- **It will store the shopping list as a document people edit.** The whole design
  is that the list is derived. If it builds an ordinary list with an "add from
  recipe" button, it has missed the point of §7.5.
- **It will store the aggregated quantity.** §7.6 explains why that is wrong; the
  grouping is worked out when the screen is drawn and never saved.
- **It will store life stage as a field.** §7.1 is explicit; check that a birth
  date is the only thing saved.
- **It will create an attendance record for everybody.** §7.2's contract is that
  no record means present.
- **It will hard-delete.** Then a deletion on one device never reaches the other,
  and the offline requeue rule in §5 turns into a resurrection bug.
- **It will always pick the top-scoring recipe.** §7.8 wants weighted random, and
  this is invisible until you generate three weeks and get the same five dinners.
- **It will build a separate mobile and desktop app.** §2 wants one app that
  answers at both widths, with only two screens genuinely forking.

Those seven are the honest test of whether the tool followed the brief or just
recognised "meal planner".
