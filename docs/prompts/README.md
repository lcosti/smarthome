# How to feed this to a no-code tool

`../rebuild-prompt.md` is the whole specification in one file — about 14,000
words. It is meant to be *read*, and it is too big for most tools' prompt boxes.
This folder is the same document sliced into nine pastable pieces, generated by
`scripts/split-rebuild-prompt.mjs`. **Edit the master, then re-run the script** —
never edit these by hand, or the two drift.

| File | Words | What it covers |
|---|---|---|
| `00-standing-brief.md` | ~2,700 | What the app is, the design system, the routes, the build order, the acceptance tests, the reference stack |
| `01-data-and-offline.md` | ~3,100 | Tables, RLS, the mutation queue and the drain loop |
| `02-shopping-list.md` | ~1,000 | The shopping list and aisle settings |
| `03-recipes-and-plan.md` | ~1,900 | Library, recipe editor, the week, deriving the list |
| `04-ingredients.md` | ~1,800 | Quantities, shopping names, aggregation, aisle guessing |
| `05-people-and-roster.md` | ~500 | People, life stages, who is eating |
| `06-generator.md` | ~1,000 | The weekly generator |
| `07-import.md` | ~500 | URL and photo import, nutrition, calendar, keepalive |
| `08-today-and-cook.md` | ~2,500 | Today, cook mode, chores, pantry |

## The shape of it, whatever the tool

1. Get `00-standing-brief.md` in front of the tool **once**, and keep it there —
   in whatever it calls project knowledge, custom instructions or a system
   prompt. It is the context every other step assumes.
2. Then send steps 1 to 8 **as separate messages, in order**, letting the tool
   finish and settle between each.
3. Attach the screenshots each step names. They settle in one look what a
   paragraph of layout prose only approximates.

Do not paste all nine at once even if they fit. The build order exists because
step 5 is much easier to get right when step 1 already works, and a tool given
everything at once will start at the generator.

## Per tool

**Lovable** — paste `00-standing-brief.md` into **Project Settings → Knowledge**.
It is prepended to every message, so you never resend it. Then send the steps as
ordinary chat messages. Attach screenshots with the image button. This is the
closest fit to how the folder is organised.

**Bolt.new** — no persistent knowledge field. Two options, and the second is
better: either re-paste the standing brief at the top of each step, or start the
project from a GitHub repo that already contains `docs/`, then say *"Read
docs/rebuild-prompt.md and docs/prompts/01-data-and-offline.md, then build step
1."* Bolt reads files in the project, so the big document costs you nothing in
the prompt box.

**v0** — has project-level instructions; put the standing brief there. v0 is
strongest on single screens, so it is worth going finer than these eight steps:
feed it one `### 6.x` section from the master document at a time.

**Replit Agent / Cursor / Windsurf** — commit the whole `docs/` folder into the
project and reference files by path. These tools read the repo, so the master
document is the better input and this folder is redundant.

**Anything with a hard context limit** — use the master document's own section
numbers. Every step here is a list of sections, so you can always go finer: send
`### 7.8` on its own if the generator is all you want.

## What to watch for

The parts a tool will most likely get wrong, in rough order of likelihood:

- **It will store the shopping list as a document people edit.** The whole design
  is that the list is derived. If it builds a CRUD list with an "add from recipe"
  button, it has missed the point of §7.5.
- **It will store the aggregated quantity.** §7.6 explains why that is wrong; the
  grouping is a render-time concern.
- **It will store life stage as a field.** §7.1 is explicit; check that a birth
  date is the only thing on the row.
- **It will materialise attendance rows for everybody.** §7.2's contract is that
  no row means present.
- **It will use argmax in the generator.** §7.8 wants weighted random, and this
  is invisible until you generate three weeks and get the same five dinners.
- **It will build a separate mobile and desktop app.** §2 wants one app that
  answers at both widths, with only two screens genuinely forking.

Those six are the honest test of whether the tool followed the brief or just
recognised "meal planner".
